# 🏗 Архітектура

Я не використовував FSD або іншу жорстко задану архітектуру.

Основний принцип:

> UI-компоненти відповідають за відображення, а робота з API та бізнес-логіка винесені в окремий шар.

Це відповідає ключовій вимозі тестового завдання — не змішувати роботу з API та бізнес-логіку безпосередньо з UI.

Приблизна структура проєкту:

```text
src/
├── api/
│   └── ...
├── app/
│    ├── _layout.tsx
│    ├── index.tsx
│    └── post/
│        └── [id].tsx
│
├── components/
│   ├── post/
│   ├── comment/
│   ├── SearchBar.tsx
│   └── ...
│
├── constants/
│   └── ...
│
├── hooks/
│   ├── post/
│   │   ├── queries/
│   │   └── mutations/
│   ├── comment/
│   └── ...
│
├── screens/
│   ├── PostDetailsScreen.tsx/
│   └── PostListScreen.tsx/
│
├── services/
│   ├── post.service.ts
│   └── comment.service.ts
│
├── styles/
│   └── ...
│
├── types/
│   ├── post.ts
│   ├── comment.ts
│   └── ...
│
└── ...
```

### Чому саме така структура?

Я розділив відповідальність між окремими шарами:

- **API** — HTTP-запити;
- **Services** — робота з даними та бізнес-логіка;
- **Hooks** — інтеграція з TanStack Query;
- **Components** — перевикористовувані UI-компоненти;
- **Screens** — композиція окремих екранів;
- **Types** — TypeScript-типи;
- **Constants** — константи застосунку.
- **Styles** — UI стилі.

Наприклад, `PostCard` не повинен знати, як саме отримується або оновлюється пост. Він отримує необхідні дані та callback-и через props.

Це дозволяє зменшити зв'язність між UI та шаром роботи з даними.

# 🧭 Навігація

## Expo Router

Для навігації я використав **Expo Router** замість ручної конфігурації React Navigation.

Expo Router працює поверх React Navigation, але додає файлову систему маршрутів.

Приклад:

```text
app/
├── _layout.tsx
├── index.tsx
└── post/
    └── [id].tsx
```

Для переходу на конкретний пост використовується динамічний маршрут:

```ts
router.push(`/post/${post.id}`);
```

### Чому Expo Router?

- зрозумілий синтаксис;
- прості динамічні маршрути;
- зручний варіант для структури цього проєкту;
- хороша інтеграція з Expo;
- структура навігації безпосередньо відображена у файловій структурі.

# 🗃 State Management

## Окремий State Manager не використовувався

Я свідомо не додавав:

- Jotai;
- глобальний Context.

Стан застосунку розділений на кілька категорій.

Повністю керується **TanStack Query**:

- пости;

- mutations;
- кеш;

### Локальне постійне сховище

Для цього використовується **AsyncStorage**:

- локально створені пости;

- видалені пости;
- локально додані коментарі;
- UI-налаштування.

### Локальний стан компонента

Для UI-стану використовується стандартний React:

```ts
useState;
useEffect;
useMemo;
useCallback;
```

Окремий глобальний state manager у цьому випадку створив би дублювання відповідальності, оскільки основна частина стану вже правильно покривається TanStack Query.


### Current User

Оскільки в межах тестового завдання не реалізована повноцінна authentication-система, поточний користувач представлений mock-даними:

export const CURRENT_USER = {
  id: 1,
  firstName: "Emily",
  lastName: "Johnson",
  fullName: "Emily Johnson",
};

Це використовується для:

визначення власника поста/коментаря;
відображення Edit/Delete actions;
передачі userId під час створення поста або коментаря.

Це свідоме спрощення саме для тестового завдання — окремий auth/state manager для одного статичного користувача був би зайвим.

💡 Чому без глобального State Manager?

У поточній архітектурі кожен тип стану має відповідальний інструмент:

Тип стану	Інструмент
Server state	TanStack Query
UI state	React useState / useRef
Persistent local state	AsyncStorage
Current user	Mock constants

Тому додавання Zustand або Redux Toolkit створило б додатковий шар абстракції без реальної користі для цього застосунку.

# 📦 Expo Go чи Development Build

Для цього проєкту обрано **Expo Go**.

Основна причина — вибір **AsyncStorage** замість MMKV.

Умови тестового прямо пов'язують вибір сховища з типом Expo-середовища:

- AsyncStorage працює в Expo Go;
- MMKV використовує native JSI/C++ код і потребує Development Build.

Тому для цього проєкту немає необхідності у власному Development Build.

---

# 💾 AsyncStorage vs MMKV

У тестовому завданні необхідно було дослідити обидва варіанти та обґрунтувати вибір.

| Характеристика              | AsyncStorage | MMKV          |
| --------------------------- | ------------ | ------------- |
| API                         | Асинхронний  | Синхронний    |
| Продуктивність              | Хороша       | Дуже висока   |
| Expo Go                     | ✅           | ❌            |
| Development Build           | ✅           | ✅            |
| Складність інтеграції       | Низька       | Вища          |
| Підходить для цього проєкту | ✅           | Також можливо |

## Чому AsyncStorage?

Застосунок не виконує велику кількість операцій зі сховищем.

Потрібно зберігати:

- локальні пости;
- локальні зміни;
- видалені пости;
- локальні коментарі;
- налаштування пошуку/фільтрації.

Для такого обсягу даних продуктивності AsyncStorage достатньо.

MMKV був би цікавішим вибором для застосунку з великою кількістю синхронних операцій зі сховищем, але в цьому проєкті його перевага не компенсує необхідність переходу на Development Build.

# 🔄 Мердж серверних і локальних даних

DummyJSON симулює `POST / PUT / DELETE`, але фактично не зберігає зміни на сервері.

Тому після повторного запиту до API локальні зміни могли б зникнути.

Для вирішення цього використовується локальний шар змін.

Загальна схема:

```text
Дані API
   +
Локальні зміни
   ↓
Реконсиляція
   ↓
Фінальний стан застосунку
```

Наприклад, сервер повертає:

```text
Post 1
Post 2
Post 3
```

Користувач видаляє `Post 2`.

У локальному сховищі зберігається інформація про видалення:

```ts
deletedPostIds = [2];
```

Після наступного запиту:

```text
Server:
Post 1
Post 2
Post 3

Local:
Post 2 → deleted
```

результат для UI:

```text
Post 1
Post 3
```

Такий підхід дозволяє зберігати результат локальних мутацій навіть після перезапуску застосунку.

Це відповідає вимозі тестового щодо persistence локальних мутацій DummyJSON.

# ⚡ TanStack Query

TanStack Query використовується як основний шар серверного стану.

Він відповідає за:

- отримання даних;
- кешування;
- infinite queries;
- refetch;
- mutations;
- optimistic updates;
- rollback;
- синхронізацію кешу.

---

# 🔑 Query Keys

Для постів використовується єдиний query key:

```ts
["posts"];
```

Він використовується як для отримання стрічки постів, так і для отримання окремого поста.

### Список постів

`usePosts` використовує `useInfiniteQuery` з query key:

```ts
["posts"];
```

Це дозволяє TanStack Query зберігати всі сторінки стрічки в одному кеші:

```text
['posts']
  ├── page 1
  ├── page 2
  ├── page 3
  └── ...
```

### Окремий пост

Для `usePost(postId)` не створюється окремий query key на кшталт:

```ts
["post", postId];
```

Замість цього використовується той самий:

```ts
["posts"];
```

а конкретний пост вибирається з уже завантажених сторінок через `select`:

```ts
select: (data) => {
  return data.pages
    .flatMap((page) => page.posts)
    .find((post) => post.id === postId);
},
```

Тобто `usePost` не виконує окремий запит для поста, якщо він уже присутній у кеші `['posts']`.

### Переваги такого підходу

- **Один кеш** для всіх постів.
- Немає дублювання даних між `['posts']` та `['post', postId]`.
- Post Details може використовувати вже завантажені дані зі стрічки.
- Після mutation достатньо оновити кеш `['posts']`, і зміни будуть доступні як у стрічці, так і на сторінці деталей.
- `select` дозволяє отримати конкретний пост без додаткового запиту.

Таким чином, структура кешу залишається простою:

```text
['posts']
     │
     ├── page 1
     ├── page 2
     ├── page 3
     │
     └── select → postId
```

Це також відповідає підходу **"reuse query cache"** — повторно використовувати вже завантажені дані замість виконання зайвих запитів.

# ♾ Infinite Query

Стрічка реалізована через `useInfiniteQuery`.

```ts
useInfiniteQuery({
  queryKey: ['posts'],
  queryFn: ...,
  initialPageParam: 0,

getNextPageParam: (lastPage) => {
    const nextSkip = lastPage.skip + lastPage.limit;

    if (nextSkip >= lastPage.total) {
      return undefined;
    }

    return nextSkip;
  },
});
```

DummyJSON використовує:

```text
skip
limit
total
```

тому наступна сторінка визначається на основі попередньої.

Після отримання сторінок вони об'єднуються:

```ts
const posts = data?.pages.flatMap((page) => page.posts) ?? [];
```

Це відповідає вимозі використати `useInfiniteQuery` з коректним `getNextPageParam`.

# 🕐 staleTime та gcTime

Для різних типів даних використовується різна політика кешування.

## Стрічка

```ts
staleTime: 30_000;
gcTime: 5 * 60_000;
```

Стрічка потенційно може змінюватися частіше, тому `staleTime` відносно короткий.

## Коментарі

```ts
staleTime: 10_000;
gcTime: 5 * 60_000;
```

Коментарі можуть змінюватися частіше, тому для них використовується коротший `staleTime`.

Головний принцип:

> `staleTime` визначається тим, наскільки ймовірно, що конкретні дані зміняться, поки користувач їх переглядає.

Такий підхід відповідає вимозі свідомо визначити різні політики свіжості для різних типів даних.

# 🚀 Повторне використання кешу

При переході зі стрічки на деталі поста немає необхідності повторно завантажувати всю інформацію про пост.

У кеші стрічки вже є:

```text
id
title
body
tags
reactions
user
```

Тому екран деталей може використати наявні дані одразу.

Схема:

```text
Feed
 ↓
TanStack Query Cache
 ↓
Post Details
 ↓
Запит тільки відсутніх даних
 ↓
Comments
```

Таким чином, при відкритті деталей користувач не очікує повторного завантаження вже отриманого поста.

Це відповідає вимозі тестового щодо `getQueryData / setQueryData / initialData / prefetchQuery` та повторного використання кешу.

# ⚡ Optimistic Updates

Для:

- створення поста;
- редагування поста;
- видалення поста;
- додавання коментаря
- видалення коментаря

використовується optimistic update.

Загальний алгоритм:

```text
onMutate
   ↓
Скасувати активні запити
   ↓
Зберегти snapshot кешу
   ↓
Оптимістично змінити кеш
   ↓
UI оновлюється одразу
   ↓
Виконати API mutation
   ↓
 ┌───────────────┐
 │               │
Успіх          Помилка
 │               │
 ↓               ↓
Синхронізація  Rollback
```

Це відповідає канонічному патерну `onMutate → onError → onSettled`, який наведений у вимогах завдання.

---

# 🔙 Rollback

Перед optimistic update створюється snapshot попереднього стану.

Наприклад:

```text
До:
Post 1
Post 2
Post 3
```

Після натискання Delete:

```text
Post 1
Post 3
```

UI змінюється одразу, не чекаючи API.

Якщо API повертає помилку:

```text
Post 1
Post 2
Post 3
```

Кеш відновлюється зі snapshot.

Таким чином користувач не бачить стан, який не відповідає фактичному результату mutation.

# 📋 Продуктивність списку

Для стрічки використовується **FlatList**.

У межах цього проєкту я не використовував FlashList, оскільки FlatList достатньо для поточного обсягу та складності даних.

Тестове завдання дозволяє використати FlatList або FlashList, але очікує розуміння:

- virtualization;
- `keyExtractor`;
- оцінки розміру рядків;
- memoization;
- стабільних callback-ів.

## Використані оптимізації

### `keyExtractor`

```tsx
keyExtractor={item => item.id.toString()}
```

Дає React Native стабільний ідентифікатор для кожного елемента.

### `React.memo`

`PostCard` мемоїзований.

Якщо конкретний пост не змінився, його компонент не повинен повторно рендеритися лише через зміну іншого поста.

### `useCallback`

`renderItem` та callback-и мемоїзовані там, де це має сенс:

```ts
const renderItem = useCallback(
  ({ item }) => (
    <PostCard post={item} />
  ),
  [],
);
```

Це допомагає уникати створення нових reference-ів функцій при кожному render.

# ⚠️ Особливість DummyJSON

DummyJSON не зберігає зміни `POST / PUT / DELETE` постійно.

Тому ці mutations використовуються як клієнтський експеримент із кешем.

Щоб користувач після перезапуску застосунку продовжував бачити свої зміни, вони додатково зберігаються в AsyncStorage.

У результаті використовується модель:

```text
Дані сервера
      +
Локальні mutations
      ↓
Об'єднаний стан
      ↓
UI
```

# ⚠️ Trade-offs

### AsyncStorage замість MMKV

AsyncStorage повільніший та асинхронний, але для обсягу даних цього застосунку його продуктивності достатньо.

MMKV був би кращим вибором для великої кількості частих операцій зі сховищем.

### FlatList замість FlashList

FlashList потенційно краще масштабується на дуже великих списках.

Проте в поточному проєкті:

- список пагінований;
- елементи відносно прості;
- FlatList використовує virtualization;
- додаткові оптимізації зменшують кількість зайвих render.

Тому використання FlashList зараз не є необхідним.

### Локальний шар mutations

Через особливості DummyJSON довелося додати локальну persistence-логіку.

Це збільшує складність, але дозволяє зберігати результат CRUD після перезапуску застосунку.

# 🎯 Висновок

Основний фокус проєкту — не кількість функцій, а якість технічних рішень.

Ключові рішення:

1. API та бізнес-логіка винесені за межі UI.
2. TanStack Query використовується як основний server-state manager.
3. Дані стрічки повторно використовуються на екрані деталей.
4. Реалізовані optimistic updates та rollback.
5. Локальні mutations DummyJSON зберігаються в AsyncStorage.
6. AsyncStorage обраний через достатню продуктивність та сумісність з Expo Go.
7. FlatList оптимізований через `React.memo`, стабільні `keyExtractor` та callback-и.
8. Create/Edit реалізовані через Gorhom Bottom Sheet.
9. Враховані Safe Areas, жести та робота з клавіатурою.

Таким чином, проєкт сфокусований на тих аспектах, які є ключовими для тестового завдання: **архітектура, TanStack Query, кешування, optimistic updates, persistence, native UX та продуктивність списків**.
